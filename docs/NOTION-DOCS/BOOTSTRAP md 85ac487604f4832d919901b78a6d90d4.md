Hey welcome to this — this is the **harness engineering bootstrapping project file** that gets **updated and replicated every time we create a new project**.

### What this file is

- The **entrypoint for the meta-project** (the harness that creates harness-based projects).
- A **portable contract** for how Claude should move through this repository’s file system.
- The place where **system-wide improvements** are recorded and then pushed “upstream” into the template so the *next* project is already hardwired with them.

### How to navigate the file system (canonical)

Start at the repo root and follow this order:

1. `CLAUDE.md` (project rules + pointers)
2. `BOOTSTRAP.md` (this file — meta workflow)
3. `docs/harness/goal.md` (definition of better + acceptance criteria)
4. `docs/harness/golden-path.md` (fresh clone/export → green)
5. `docs/harness/sources.md` (pins + provenance)
6. `docs/harness/memory.md` (invariants + decisions)
7. `.claude/` (runtime controls: settings, rules, agents, skills)
8. `schemas/` + `examples/` (contracts + canonical examples)
9. `compiler/` (spec compiler outputs/checklists)
10. `runs/` (append-only execution history)

### Core fractal rule (self-replication)

When prompted for a **use case**, generate a new project by copying the template and customizing only the project-specific nucleus docs.

- Template source: `_harness_template/`
- New projects destination: `projects/<project-name>/`

---

### Folder-structure principles (simultaneous, non-competing)

These principles apply **at the same time**. Vertical slices do not replace atomic/cellular structure—they are implemented *using* it.

1. **Vertical**: organize by *end-to-end capability* (a slice contains UI/logic/data/docs for that capability).
2. **Atomic**: within a slice, build reusable “atoms” (smallest useful modules/files/templates) that compose upward.
3. **Cellular**: each slice is a “cell” with clear boundaries, contracts (schemas), inputs/outputs, and its own run log history.

### Practical rule

- **Slice = Cell** (a directory)
- **Cell contains Atoms** (schemas, examples, skills, docs, CSVs)
- **Cells compose into the System** (the repo)

### Upstreaming rule (self-improving)

When a change in a specific project would improve the system as a whole:

1. Record the improvement in that project’s run log.
2. Promote it into `_harness_template/` (the meta-project) so future projects inherit it.
3. Update this file (`BOOTSTRAP.md`) if the workflow itself changed.

### What to do now (boot sequence)

1. Normalize the exported portable harness package into `_harness_template/`.
2. Create a plan file (`bootstrap.plan.md`) that defines the steps + evaluation knobs.
3. Scaffold the agent team and one primary skill per agent.
4. Prompt the user for a use case.
5. Generate the first fractal project under `projects/`.

### Acceptance criteria (for this meta-project)

- A fresh export or clone can reach “green” using only repo files.
- Every artifact has a schema + example + validator.
- New projects can be generated without web research.
