### Purpose

This file defines the canonical task list workflow. Claude must use this instead of inventing ad-hoc task formats.

### Where tasks live (portable)

- Global (meta-project): `runs/tasks/<agent>.md`
- Per-project: `projects/<project>/runs/tasks/<agent>.md`

### Task format (stable)

Each task list is a markdown checklist:

- [ ]  **Task title** — short, testable deliverable
    - Owner: `<agent-name>`
    - Inputs: …
    - Outputs: …
    - Validation: …
    - Links: …

### Rules

- Every task must have an owner (one lane).
- Every task must declare outputs and validation.
- When a task is completed, record it in the current run log and update the task to `- [x]`.
- If a task reveals a reusable improvement, upstream it into the template and note it in `BOOTSTRAP.md`.

## Bootstrap task list (what Claude must do every time)

Use this task list as the default checklist when generating a new project from the meta-harness.

### Principles check (must enforce in structure)

- Vertical / Atomic / Cellular apply simultaneously:
    - **Vertical**: create a project as vertical slices (end-to-end capability folders).
    - **Atomic**: each slice must contain composable atoms (small reusable files/modules + schemas/examples).
    - **Cellular**: each slice must declare its contracts and boundaries (schemas + inputs/outputs + run log entries).

### 0) Read order (must follow)

- Read `BOOTSTRAP.md` first (root entrypoint).
- Then read `CLAUDE.md`.
- Then read `docs/harness/*` (goal, golden path, sources, memory).
- Then read `.claude/` documentation/spec and verify the expected structure exists.
- Then read `schemas/` and confirm required schemas exist for the artifacts you will touch.

### 1) Create the new project folder (fractal replication)

- [ ]  Create `projects/<project-name>/` as a copy of `_harness_template/`.
    - Owner: `planning-agent`
    - Outputs: folder created, nucleus docs present
    - Validation: the file tree contains all required nucleus docs + `.claude/`

### 2) Prompt the user for the use case (required questions)

- [ ]  Ask the user: project name, one-sentence purpose, what “green” means, constraints, and any data domains.
    - Owner: `planning-agent`
    - Outputs: answered inputs recorded into the plan + goal docs
    - Validation: `docs/harness/goal.md` contains measurable acceptance criteria

### 3) Configure the .claude control surface (must match Claude Code spec)

- [ ]  Ensure `.claude/settings.json` exists and is project-scoped.
    - Owner: `planning-agent`
    - Outputs: `.claude/settings.json`
    - Validation: file exists; referenced by `CLAUDE.md`
- [ ]  Ensure `.claude/rules/`, `.claude/agents/`, `.claude/skills/` exist.
    - Owner: `planning-agent`
    - Outputs: directories + starter README files
    - Validation: directories exist

### 4) Databases (corporate Mac baseline: CSV-only)

- [ ]  Create `backend/data/` and seed the canonical CSV “databases”.
    - Owner: `sources-agent`
    - Outputs: `backend/data/crm.csv`, `backend/data/tasks.csv`
    - Validation: CSV files contain the required header row and at least one example row
- [ ]  If the project needs additional databases, add more CSVs under `backend/data/` and document them under `schemas/`.
    - Owner: `sources-agent`
    - Outputs: new `backend/data/<domain>.csv` + schema reference in `schemas/`
    - Validation: schema exists and the example CSV matches its column contract

### 5) Run logging + self-improvement (meta-harness requirement)

- [ ]  Create `runs/0001.md` and record the bootstrap run.
    - Owner: `evaluation-agent`
    - Outputs: `runs/0001.md`
    - Validation: includes links/pointers to plan, artifacts, and the “keep/revert” decision
- [ ]  If any improvement applies globally, upstream it into `_harness_template/` and update `BOOTSTRAP.md`.
    - Owner: `evaluation-agent`
    - Outputs: template updated + upstream note
    - Validation: change is reflected in template and documented in run log
