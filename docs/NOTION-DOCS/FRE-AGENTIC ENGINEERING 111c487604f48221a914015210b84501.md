## 1) Principles (fractal / atomic / vertical / cellular)

- **Fractal**: Every project repeats the same structure at smaller scales (workspace → program → project → module → task).
- **Atomic**: Smallest useful units (“atoms”) are versioned and reusable; larger constructs are composed.
- **Vertical**: Prefer *vertical slices* (end-to-end capability) over horizontal layers.
- **Cellular**: Each cell has clear boundaries, contracts, inputs/outputs, and can be swapped without breaking the organism.

## 2) Definitions

- **Harness**: The system around the model/tools (plans, contracts, configs, tests, observability, guardrails) that makes work reproducible and safe.
- **Project Space / Lab**: A controlled environment for building + validating harness modules, templates, and standards.

## 3) Non-negotiable outcomes (what “done” means)

1. **Composable building blocks**: modules/templates/configs that can be assembled into a new project quickly.
2. **Reproducible execution**: same inputs ⇒ same outputs (or differences are detected + explained).
3. **Persistent configuration**: durable state that survives sessions and is portable across machines.
4. **Accessible by default**: docs, runbooks, and workflows are readable + runnable by a new collaborator.
5. **Self-validation**: tests + checks that prevent drift and catch regressions.

## 4) The Harness “Kit” (core components)

### A) Project skeleton (the fractal template)

- **00-Overview** (what/why, definition of success)
- **01-Architecture** (system diagram, contracts)
- **02-Execution** (how to run, how to resume)
- **03-Configs** (global + project + local overlays)
- **04-Data** (datasets, schemas, provenance)
- **05-Observability** (logs, metrics, traces)
- **06-Validation** (unit/integration/e2e checks)
- **07-Operations** (release, rollback, incident playbooks)

### B) Configuration model (persistent + layered)

- **Global defaults** (applies everywhere)
- **Project config** (checked in; portable)
- **Local overrides** (not checked in)
- **Secrets** (never in repo; referenced via a secrets provider)

### C) Contracts-first design

- **Event contracts**: what events exist + required fields.
- **IO contracts**: every module declares inputs/outputs.
- **Tool contracts**: typed schemas for tools/agents.

### D) Validation harness

- Golden tests (known inputs/expected outputs)
- Replay tests (can re-run a session deterministically)
- Drift detection (config/schema changes trigger checks)

### F) Validation sequence (the gate that always runs)

This is the standard validation sequence that happens whenever a project is bootstrapped from this lab (and whenever you evaluate changes). It is intentionally layered: cheap checks first, expensive checks last.

1. **Contract validation**: validate required artifact structure exists (nucleus docs + required folders), and schemas/contracts are present and parseable.
2. **Config validation**: ensure config layers resolve cleanly (global/project/local), required env vars are present, and secrets are referenced (not hard-coded).
3. **Static checks**: formatting/lint/type checks (language-specific) + basic policy checks (no forbidden files, no credential leakage, no missing runbook links).
4. **Unit tests**: fast, deterministic tests for small modules.
5. **Integration tests**: verify module boundaries + IO contracts using representative fixtures.
6. **Golden tests**: run known inputs → compare outputs to expected snapshots (“goldens”). Fail if drift is not explicitly accepted.
7. **Replay tests**: re-run a recorded session deterministically (or within declared tolerances) and compare trace/output hashes.
8. **Observability checks**: verify logs/metrics/traces were emitted and include run IDs + cost accounting fields.
9. **Drift detection**: compare schema/config versions + artifact registry expectations; create a drift report if anything changed unexpectedly.
10. **Publish decision**: if all gates pass, promote the change (or component) to the catalog; otherwise emit a failure-mode report + required remediation steps.

**What this looks like in practice**: the project’s “golden path” should include a single **Validate** step that runs these checks in order (often via a `make validate` / `task validate` / `just validate` style command), producing one consolidated report plus machine-readable results for automation.

### E) Observability + economics

- Cost/token accounting, rate limits, budgets
- Trace IDs for every run
- Structured logs for every action

## 5) Lab workflow (how new projects get born)

1. **Design the slice**: define the vertical slice capability + success criteria.
2. **Declare contracts**: inputs/outputs, schemas, invariants.
3. **Implement module**: code + config + docs together.
4. **Prove reproducible**: run tests + replay.
5. **Promote to catalog**: publish as a reusable harness component.

## 10) Claude Code “self-grounding” (docs + changelog as first-class inputs)

This harness must be grounded in **Claude Code’s own specifications**, especially the **.claude directory contract** and the official changelog.

### A) Canonical sources (authoritative)

- **.claude directory spec**: [https://code.claude.com/docs/en/claude-directory](https://code.claude.com/docs/en/claude-directory)
- **Changelog**: [https://code.claude.com/docs/en/changelog](https://code.claude.com/docs/en/changelog) (generated from `CHANGELOG.md` on GitHub)

### B) What this means in practice (non-negotiable behaviors)

1. **Follow the .claude contract** for where configuration, instructions, hooks, skills, agents, and memory live.
2. **Log every meaningful action** (tool call, file edit, permission decision, hook outcome) as an append-only record.
3. **Track runtime drift**: whenever Claude Code changes (version / behavior), record the version and reconcile any spec changes that affect this harness.

### C) Minimum required .claude layout (project-scoped)

The harness should treat these as the “minimum viable livelihood” for Claude Code operation:

- `CLAUDE.md` (root): project context + conventions loaded every session
- `.claude/settings.json`: permissions, hooks, env, model defaults
- `.claude/rules/*.md`: topic-scoped rules (optionally path-gated)
- `.claude/skills/<skill-name>/SKILL.md`: reusable skills invoked by `/name`
- `.claude/agents/*.md`: subagent definitions
- `.mcp.json` (root): team-shared MCP servers (project only)

### D) Global vs project scope (don’t mix them)

- **Project scope**: `.claude/` + root `CLAUDE.md` + `.mcp.json` (commit these to share with collaborators)
- **Global scope**: `~/.claude/` (personal settings, plugins, caches, transcripts, auto-memory)

### E) “Every time it does something, it makes note of that” (logging contract)

Define an append-only log (human + machine readable) that captures:

- timestamp, session_id / run_id, project path
- action type (prompt, tool call, file edit, decision, hook)
- inputs/outputs hashes (or pointers), and resulting artifacts
- Claude Code version (`claude --version`) at time of action

<aside>
🧷

**Implementation note**: Determinism comes from encoding this behavior as Claude Code hooks (pre/post tool use, prompt submit, stop), not from “remembering to do it.” This is how we make it part of the harness’s livelihood.

</aside>

## 11) Foundational “standard markdown files” (operational nucleus)

These are the minimum docs the harness should always ship with. Think of them as the **operating nucleus**: they define identity, memory, goals, the happy-path workflow, and provenance.

> Note on naming: Claude Code looks for `CLAUDE.md` specifically (capitalization matters in many repos). If you prefer `Claude.md`, keep it as a human alias, but treat `CLAUDE.md` as canonical.
> 

### A) Required files (minimum set)

1. **`CLAUDE.md`** (root)
2. **`memory.md`**
3. **`goal.md`**
4. **`golden-path.md`**
5. **`sources.md`**

### B) Where they live (suggested, simple + consistent)

- `CLAUDE.md` at repo root (Claude Code canonical)
- Put the rest under `docs/harness/`:
    - `docs/harness/memory.md`
    - `docs/harness/goal.md`
    - `docs/harness/golden-path.md`
    - `docs/harness/sources.md`

Then, in `CLAUDE.md`, include a short “table of contents” that points at those four docs.

### C) What else is needed to make this truly foundational?

To make those files *operational* (not just informational), you also want these “enforcement surfaces”:

- **`.claude/settings.json`**: permissions + hooks + env defaults (turn rules into runtime behavior)
- **`.claude/rules/`**: smaller, topic-scoped constraints (keeps `CLAUDE.md` from becoming a junk drawer)
- **Changelog pin**: a line in `sources.md` capturing the Claude Code version used (`claude --version`) at time of run
- **Append-only action log**: one canonical log location + schema (so every run is auditable/replayable)

### D) Minimal templates (starter text)

#### 1) `CLAUDE.md`

- Project one-liner + “what are we building”
- Canonical links to:
    - `docs/harness/goal.md`
    - `docs/harness/memory.md`
    - `docs/harness/golden-path.md`
    - `docs/harness/sources.md`
- Hard rules (short list)
- How to run / validate (first command, first test)

#### 2) `memory.md`

- Stable facts (vocabulary, invariants, definitions)
- Decisions that must not be re-litigated
- “What changed since last run” (short rolling log)

#### 3) `goal.md`

- “Done means…” acceptance criteria (measurable)
- Non-goals
- Constraints (time/budget/tooling)

#### 4) `golden-path.md`

- The happy-path sequence for a fresh clone:
    1. Setup
    2. Configure
    3. Run
    4. Validate
    5. Ship / handoff
- The exact command(s) for each step

#### 5) `sources.md`

- Authoritative specs (Claude Code docs links)
- Workspace anchors (Notion pages that are canonical for this project)
- Version pins (Claude Code version, key deps)
- Provenance rules (what can be trusted vs. must be verified)

## 12) Agentic team design (narrow scopes + one skill per agent)

When we add a new purpose to this harness, we don’t just add rules—we add an **agentic team** whose members have **non-overlapping scopes** and **one primary skill each**.

### A) Team rules (non-negotiable)

1. **No scope overlap**: each agent owns a distinct “lane” (inputs/outputs + responsibilities are explicit).
2. **One agent ⇄ one primary skill**: each agent has exactly one “main” skill (it can still call other skills, but only one is its core identity).
3. **Each team has its own task list**: tasks are assigned to the smallest responsible agent.
4. **Planning always comes first**: if a plan exists, we run the **Planning Agent** before any other agent.

### B) Claude Code alignment: frontmatter is first-class for skills + subagents

Claude Code skills and subagents are **Markdown files with YAML frontmatter**:

- Skills: `.../skills/<skill-name>/SKILL.md` uses YAML frontmatter + markdown instructions.[[1]](https://code.claude.com/docs/en/skills)
- Subagents: `.claude/agents/*.md` uses YAML frontmatter + a system prompt body.[[2]](https://code.claude.com/docs/en/sub-agents)

### C) Standardized frontmatter (our house spec)

We will use YAML frontmatter for **all harness-controlled artifacts** that represent an executable role or procedure:

- `SKILL.md` (skills)
- `.claude/agents/*.md` (subagents / teammates)
- `*.plan.md` (plan files; see next section)

> Practical constraint: keep skill `description:` **single-line** to reduce YAML parser brittleness (common failure mode in the wild).
> 

### D) Recommended team shape (starter roster)

- **planning-agent**: produces/maintains the plan + acceptance criteria; owns `goal.md` alignment.
- **sources-agent**: maintains `sources.md` + version pins + provenance rules.
- **golden-path-agent**: maintains `golden-path.md` + validation gate + failure-mode playbook.
- **memory-agent**: curates `memory.md` (stable facts + decisions) and prevents drift.
- **evaluation-agent**: runs the autoresearch-style loop: proposes small changes, runs evaluation, records results, reverts if worse.

Each of the above should have:

- a subagent definition (`.claude/agents/<name>.md`)
- a single primary skill (`.claude/skills/<skill-name>/SKILL.md`)
- an explicit task list (tracked via runs/logs + the harness task system)

## 13) Planning files: YAML frontmatter (top) + YAML “bottom matter” (end)

We’re adopting a **dual-metadata** pattern for plans:

1) **Top YAML frontmatter** (tool-friendly indexing: name, overview, status, owners)

2) **Bottom YAML “bottom matter”** (execution config + evaluation knobs)

### A) Why both?

- Frontmatter is great for **indexing + UI rendering** (e.g., Cursor-style `.plan.md` rendering via YAML frontmatter conventions).
- Bottom matter is great for **execution knobs** because it can be appended/updated without disturbing the narrative plan.

### B) File naming convention

- Plans should end with: `*.plan.md`

### C) Minimum plan contract

Plan docs must contain:

1. **Goal link** → points to `docs/harness/goal.md`
2. **Acceptance criteria** → pass/fail checks
3. **Task graph** → ordered + parallelizable steps
4. **Validation commands** → exact commands to prove correctness
5. **Evaluation config** → bottom matter YAML block

### D) Bottom-matter YAML (our proposal)

At the end of the plan file, add a fenced YAML block:

```yaml
# plan-config (bottom matter)
run:
  iteration_budget:
    wall_clock_minutes: 10
    max_turns: 50
  quality_gate:
    required_checks:
      - "lint"
      - "tests"
  logging:
    action_log: ".claude/logs/actions.jsonl"
  scoring:
    primary_metric: "goal_pass_rate"
    secondary_metrics:
      - "time_to_green"
      - "manual_interventions"
```

## 14) Meta-harness linkage (self-improving outer loop)

We are explicitly aligning this harness with the **Meta-Harness** concept: an outer loop that proposes harness changes, evaluates them, stores traces/scores, and repeats.[[3]](https://arxiv.org/abs/2603.28052)

### A) The outer loop (markdown-first)

1. Propose a small harness change (docs/rules/skills/agents/config).
2. Run the golden path + evaluation gate.
3. Score against `goal.md`.
4. Persist traces: run log + action log + diff summary.
5. Keep if better; revert if worse; record the decision.

### B) Where this lives (portable contract)

All durable contract lives in-repo as Markdown + Claude Code config:

- `docs/harness/*` (goal/memory/golden-path/sources)
- `.claude/*` (settings/rules/skills/agents)
- `runs/*` (iteration history + evaluation records)
